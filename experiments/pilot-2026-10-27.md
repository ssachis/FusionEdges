# Pilot, 27 Oct 2026: Next.js navbar into a React (CRA) site

**Question.** Does the compatibility report (condition D) help a fixed coding agent compared to the agent alone (A)?
**Tasks.** 2 React CRA sites × 2 Next.js + Tailwind donors, component `navbar`, 1 run per condition
(`experiments/next-to-react-navbar.json`). Model: Gemini, pinned by provider but not by model (see problem 1).
**Data.** Every run, its checks, its full code diff (`diff_files`), every comparison and every review are in
`output/runs.db`. The run log is `experiments/logs/pilot-20261027-020233.log`; the review is
`experiments/reviews/pilot-2026-10-27.json` (also loaded into the `reviews` table).

## Problems found by reading the diffs (not visible in the scores)

1. **Models were mixed.** Gemini returned 503 "high demand" and then a quota error, and FusionEdges fell back
   from `gemini-3.6-flash` to `gemini-3.5-flash-lite` mid-experiment. Fix: comparisons whose runs used different
   models are now `inconclusive` automatically. Still to do: pin one model and stop instead of falling back.
2. **Checks v1 were wrong in 6 of 8 runs.**
   - *Rendered* looked for donor component names being used as JSX. It failed every in-place rewrite of the site's
     existing navbar (4 runs) and passed a run whose new files nothing imported, because `Link` matched
     react-router's `Link`.
   - *Only one navbar* counted react-router's `Navigate` as a second navbar.
   - *Donor code present* only accepted the donor's component names, so it penalised adapting the code.
   - Nothing checked the site's own scripts, so the one real regression (row 1) scored as a pass.
3. **A truncated answer silently dropped the mount step** (row 2, D). The log says "answer was cut off; asking it to
   continue", the continuation never rewrote `Header.js`, and the run still "passed".
4. **The report can mislead (a matrix error, in the proposal's terms).** In rows 3 and 4 the report told the agent to
   express Tailwind as inline styles; inline styles cannot express `md:flex`, so the agent hid the desktop links.
   Neither the build nor any static check sees this.
5. **12 older runs (15 Oct) count as "done" although the AI call failed** (quota / retired model). Their comparisons
   are now `inconclusive` when the agent errored.

## What changed in FusionEdges (checks v3)

- *Rendered*: the new code must be reachable from the app's entry through imports (in-place rewrites pass,
  orphaned files fail and are named).
- *Only one navbar*: component names are matched on whole camelCase words (`NavBar`, `SiteHeader` count;
  `Navigate`, `NavLink` do not).
- *Donor code present*: also passes when 3+ of the donor component's distinctive strings carried over (adapted).
- New check *The site's own scripts still find their elements*, from the scanner's `host-script-coupling` fact,
  computed the same way for both conditions.
- Comparisons: different models or a failed AI call → `inconclusive`.
- Old check results are kept in each `run.json` under `checks_history`; `python3 -m fusionedges rescore` re-runs the
  checks without AI calls.

Changing the checks changes the success criteria. That is what the pilot is for; freeze them before the main runs.

## Browser check (added 27 Oct, 10:40)

Every built result was opened in Chromium at 1280 px and 390 px, scrolled, and its visible navbar links and page
errors recorded (`experiments/browser/2026-10-27/`: screenshots, `results.json`, `check.js`). The agent-alone run of
task 2 has no build, so it could not be opened. Review: `experiments/reviews/browser-2026-10-27.json`.

| Task | Same model? | Agent alone (browser) | With report (browser) | Verdict |
|---|---|---|---|---|
| React-Portfolio ← muhammad-fiaz | yes | works, but **3 page errors on scroll** (`main.js` → `.navbar`) | works, no scroll errors | **improved** |
| React-Portfolio ← timlrx blog | no | build failed | **original navbar still shown** | no change |
| soumyajit Portfolio ← muhammad-fiaz | no | works at both widths | **desktop links hidden** (inline `display:none`) | worse |
| soumyajit Portfolio ← timlrx blog | yes | **unstyled** (Tailwind classes, no Tailwind) | works at both widths (Bootstrap `d-none d-md-flex`) | **improved** |

**Both same-model pairs: improved.** The two pairs that mixed models: one no change, one worse. Small numbers, but it is
the first evidence that holds up when checked in a browser, not just by static checks.

The browser corrected my code reading once: in task 4 I predicted hidden desktop links in the report run, but
Bootstrap's `d-md-flex` (`!important`) overrides the inline style. Lesson: code reading is a hypothesis; the browser
decides. Two page errors appear in every build of React-Portfolio, including the run that kept the original navbar,
so they were there before any agent touched it.
