# FusionEdges evaluation protocol

Status: development plan; held-out suite and statistical analysis must be frozen before testing. The seven old v1 runs remain diagnostic evidence, separate from corrected comparisons.

## Research question
Can compatibility-guided escalation reduce total AI tokens and elapsed time per successful component transfer while preserving component quality and unrelated host behavior?

## Scope and counting
React and Next.js components, beyond navigation. Record actual donor/target framework and version, immutable commits, component family and distinct repository pairs. A task is one donor-component/target integration specification; a run is one method applied to one task. Repeats are not new independent tasks.

Aim for 100–200 total executions within available quota, rather than promising 100–200 independent cases. A provisional upper allocation is six diagnostic runs, 120 core runs (60 matched tasks × two methods), 48 repetitions (12 of those tasks × two methods × two additional repeats), and 24 memory-ablation runs (12 separate tasks × two report-memory settings): 198 executions. This is a capacity plan, not an evidence threshold or power calculation. Reduce breadth before sacrificing checks and review.

## Development and held-out boundary
1. Use the six diagnostic executions to find infrastructure, styling, mounting and preservation failures.
2. Fix and rerun diagnostic failures under a new version; retain all attempts and resource usage.
3. Before selecting/evaluating final test tasks, freeze routing rules, prompts, model, retrieval procedure, limits, verification, metric definitions and code/artifact hashes.
4. Separate development and held-out repositories by repository identity, including donor and target roles. Pin commits; do not tune against held-out failures. Reuse of a development repository is development evidence, even with another commit/component.
5. Register the final task manifest and eligibility checks before running either method. No success-dependent exclusions. Collect several component families and repository pairs; report results by target framework and component.

## Matched comparison
Primary arms: agent-only versus automatic FusionEdges. Same task specification, pinned source/donor commits, Gemini model, supplied acceptance criteria, hardware, warm dependency setup, browser viewports and permitted framework changes. Freeze balanced/randomized order before execution. Define equal total token/time/repair ceilings for the core benchmark in executable guards before freezing it; report any method-specific tool/repair limits. Do not silently change provider or model when quota is reached.

Both methods receive the same preservation and behavioral requirements. Reports and code retrieval generated by FusionEdges are part of its measured cost. Stop or mark incomplete on infrastructure/quota failure; retain attempts and their known costs. Do not compare a completed arm with a missing partner.

## Success and review
Publish separate build, browser/contract, visual-fidelity, behavior and host-preservation results. A build pass alone is not transfer success. Capture desktop and mobile full-page and component screenshots plus interaction states. Preserve original host screenshots and full text/content assertions, not only headings.

Create randomized, label-blinded packets with donor reference, original target, output screenshots and diffs. Human reviewers score donor fidelity, task fulfillment, responsiveness and preservation, and note concrete defects. Report reviewer identity/count and disagreement handling. Assistant reviews may supplement this but must be labeled unblinded AI reviews, not independent human evaluation. Do not claim full visual success before review.

Failures remain in denominators. Categorize infrastructure/provider, donor selection, missing mount, style loss, behavior/accessibility, dependency/build, unrelated edits and verification gaps. Keep automatically passing but visually incorrect cases visible.

## Metrics and interpretation
Primary quality endpoint: verified, visually reviewed task success. Efficiency: all-attempt AI tokens and end-to-end elapsed time divided by successful transfers; undefined if there are no successes. Also publish paired success differences, token/time distributions, retries, regression rate, files/lines added/modified/deleted, checks unavailable, and qualitative examples. Include report/retrieval/repair costs; report whether provider reasoning tokens are included or unreported. Separate setup time from timed transfer time with an identical warm-cache policy.

Use paired analyses. Account for shared repositories when estimating uncertainty; report cluster counts and limitations. Choose the resampling procedure before observing held-out results. Do not infer quality preservation from a nonsignificant difference, or generalization from repeated familiar repositories. A provisional five-percentage-point quality margin may be considered, but justify it and assess precision before making a non-inferiority claim; the planned sample may be inadequate. If the interval is inconclusive, say so.

## Memory ablation
Memory off and on must use the same frozen core pipeline and report stage, with separate tasks excluded from memory. Populate memory only from reviewed development cases; freeze content, retrieval index and hashes before testing. Exclude the task itself, alternate commits/forks of its repositories, and held-out outcomes. Count retrieval/prompt tokens and latency. A memory benefit is an experimental result, not an assumption.
